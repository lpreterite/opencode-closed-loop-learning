# 改版方案：基于六类知识分类模型的闭环学习系统重构

> Revamp Plan — v1
> 基于 `AI记忆系统-知识分类模型` 对闭环学习系统进行体系化重构

**文档状态**：草案
**当前版本**：v0.1
**最后更新**：2026-05-13

---

## 1. 为什么要改版

### 1.1 当前系统的局限

OpenCode 闭环学习系统当前采用 **4 类经验**（tp/wf/cs/ap），而我的知识分类模型提出了 **6 类业务对象**（案例/偏好/反模式/方法论/领域工作流/领域知识）。

当前系统的问题：

| 问题 | 表现 | 后果 |
|------|------|------|
| **wf/ 混杂** | 流程经验混装了通用方法论和领域特定工作流 | Agent 跨项目时无法判断"这个流程是否适用于当前系统" |
| **缺少偏好** | 没有 pf/ 分类 | 无法记录个人倾向，"队长是什么样的人"没有载体 |
| **缺少领域知识** | 没有 dk/ 分类 | 稳定约束和配置事实散落在各处或被当成案例 |
| **加载协议单一** | 只按"task type"匹配 | 没有利用知识的抽象层次做差异化加载 |
| **蒸馏规则粗糙** | 简单的"用户纠正 → 提取" | 没有成熟的时机判断（第几次出现才问用户） |

### 1.2 改版目标

1. 当前 **5 个目录** → 新的 **7 个目录**（含保留的 tp/ + 6 类业务对象）
2. 加载协议从"任务类型匹配"升级为"三维定位 + DAG 蒸馏"
3. 蒸馏规则从"被动纠正"升级为"分类型分阈值的半自动时机判断"

| **流程 wf/git-commit** | → | **方法论 method/** | 迁移：这是通用方法论 |
| **流程 wf/xxx-业务特定** | → | **领域工作流 dw/** | 保留在业务工作流 |

| **流程 wf/设计验收等** | → | **领域工作流 dw/** | 这是 OpenCode 特定的协作流程 |
| **——** | → | **偏好 pf/** | 新建 |
| **——** | → | **领域知识 dk/** | 新建 |

### 2.2 最终目录结构

```
~/.config/opencode/skills/
├── experience-index/   # 经验路由索引（更新）
├── tp/                 # 工具优先级（保留）
├── method/             # 方法论 — 通用可迁移方法（从 wf/ 拆分）
├── dw/                 # 领域工作流 — 绑定特定系统/业务的步骤
├── cs/                 # 案例 — 特定场景事件（保留）
├── pf/                 # 偏好 — 个人倾向（新建）
├── dk/                 # 领域知识 — 已确认的稳定约束（新建）
└── ap/                 # 反模式（保留）
```

### 2.3 关于 tp/ 的定位

`tp/`（工具优先级）在当前系统中是"4 类之一"，在新模型中应视为**方法论的子集**——工具选择策略属于通用方法论范畴。但由于 OpenCode 的 tool-use 是 Agent 的核心能力，保留 tp/ 作为独立分类可提高首次加载的精确度。也可在后续迭代中并入 method/。

## 3. 三维加载协议

### 3.1 新模型的加载决策树

不再只是"任务类型 → 加载经验"，而是基于三维定位做智能选择：

```
遇到任务
  ↓
定位任务在三轴上的位置：
  A轴：具体 ↔ 抽象（这个任务是具体操作还是需要抽象判断？）
  B轴：通用 ↔ 专业（这个任务是通用能力还是领域特定？）
  C轴：主观 ↔ 现实（这个任务涉及个人风格还是世界约束？）
  ↓
匹配对应象限的经验类型 → 按成熟度L0-L3选择加载深度
```

### 3.2 三维定位 → 经验类型匹配

| 任务特征 | 优先加载 |
|---------|---------|
| 具体 + 通用 → "怎么做某个操作" | tp/ |
| 具体 + 中性 → "之前遇到过类似情况吗" | cs/ |
| 偏抽象 + 通用 → "这类问题通用的解法" | method/ |
| 偏抽象 + 专业 → "我们这个系统怎么做" | dw/ |
| 中间 + 专业 → "我们这个系统的限制是什么" | dk/ |
| 偏具体 + 主观 → "队长喜欢什么风格" | pf/ |
| 最抽象 + 主观 → "什么绝对不能做" | ap/ |

### 3.3 成熟度驱动的加载深度

知识的成熟度决定加载策略：

| 成熟度 | 知识状态 | 加载策略 |
|--------|---------|---------|
| L0 | 经历了但没记录 | 依赖工作记忆（当前会话上下文） |
| L1 | 案例被记录 | 按需索引（语义检索） |
| L2 | 提炼出偏好/领域知识 | 触发加载（遇到相关场景时自动加载标题+摘要） |
| L3 | 归纳出方法论/工作流/反模式 | 按需展开（需要时才加载全文） |

## 4. DAG 蒸馏规则

### 4.1 知识蒸馏 DAG

当前系统的"用户纠正 → 提取"是一条直线。新模型采用有向无环图：

```
经历(L0)
  ↓ 捕获
案例(L1)
  ↓
├── 反思感受 → 偏好(L2)          ← 向内，关于身份
└── 确认因果 → 领域知识(L2)       ← 向外，关于约束
       ↓ 归纳
       ├── 方法论(L3)             ← 通用，跨域可迁移
       ├── 领域工作流(L3)         ← 专业，绑定业务
       └── 反模式(L3)             ← 跨域，反向蒸馏
```

### 4.2 蒸馏时机判断（对应你的 5.5 节）

当前系统"任务完成时问用户"太粗糙。新模型按类型分阈值：

| 蒸馏路径 | 最小支撑条件 | 用户介入时机 |
|---------|------------|------------|
| 经历 → 案例 | 值得记录时 | ✅ 直接记录，不问 |
| 案例 → 偏好 | ≥1 案例 | ❓ 第1次问用户，之后自动 |
| 案例 → 领域知识 | ≥2 案例 + 因果可复现 | ❓ 第2次问用户 |
| 案例+领域知识 → 领域工作流 | ≥3 同类案例 | ❓ 第3次问用户 |
| 跨域流程 → 方法论 | ≥2 不同领域同型流程 | ❓ 第2次问用户 |
| 失败案例 → 反模式 | ≥2 不同场景失败 | ❓ 第2次问用户 |

### 4.3 蒸馏约束

| 约束 | 理由 |
|------|------|
| **案例是唯一起点** | 没有经历就没有知识 |
| **不中断执行流** | 蒸馏是闲时操作，任务中不提 |
| **默认生效，静默通过** | 知识创建后默认生效，出问题才纠偏 |
| **反模式必须稀少** | 反模式不应该和案例数量相当 |

## 6. AGENTS.md 改版草案

```markdown
# 闭环学习系统 - 全局基座（v2 - 六类知识模型）

## 经验加载协议

当遇到以下场景时，先使用 skill 工具加载 experience-index：
- 开始复杂任务前 → skill({ name: "experience-index" })

加载策略（三维定位法）：
1. 判断任务在三维空间中的位置：
   - A轴：具体 ↔ 抽象（操作型 vs 判断型）
   - B轴：通用 ↔ 专业（跨项目 vs 本系统特有）
   - C轴：主观 ↔ 现实（个人偏好 vs 客观约束）
2. 根据定位匹配 6 类业务对象 + tp/
3. 根据成熟度 L0-L3 决定加载深度
4. 不要一次加载超过 3 条经验（节省上下文）

## 经验沉淀判断规则（DAG 蒸馏）

在以下时机主动评估是否值得提取经验：
1. 经历发生后 → 判断是否值得记录为案例
2. 案例积累到阈值时 → 判断是否需要提炼为新知识
3. 用户纠正时 → 触发失败分析，修改或新建反模式

蒸馏约束：
- 案例是唯一起点，不问用户直接记录
- 偏好第 1 次问用户，之后自动确认
- 领域知识第 2 次问用户，第 3 次自动晋升
- 方法论/工作流第 3 次同类场景问用户
- 反模式第 2 次不同场景失败问用户
- 不中断执行流：蒸馏只在闲时进行
```

## 8. 变更风险与应对

| 风险 | 概率 | 应对 |
|------|------|------|
| 现有经验路径失效 | 中 | 迁移时保留软链接或一次性全部迁移 |
| AGENTS.md 更新后旧会话不兼容 | 低 | 经验加载都是按需的，AGENTS.md 只在会话启动时加载 |
| 三维定位增加 Agent 判断负担 | 中 | 先简化：三维定位作为 AGENTS.md 的指导原则，不在每次加载时都做完整分析 |
| tp/ 的归属争议 | 低 | 暂保留 tp/ 独立，后续迭代视情况合并入 method/ |
