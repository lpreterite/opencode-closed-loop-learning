# 经验管理

> Experience Management — v3

**文档状态**：已发布
**当前版本**：v0.3
**最后更新**：2026-04-07

> **设计原则变更**：删除"成功计数验证"，改为"失败驱动修正"。用户只感知失败，不感知成功；失败是唯一的验证信号。

---

## 1. 核心洞察

### 1.1 用户的感知边界

- **任务顺利** → 用户觉得 AI"本来就该这样"，**无感知**
- **任务卡住** → 用户介入指导 → **意识到 AI 缺了什么**

### 1.2 为什么不能用成功来验证

| 场景 | 用户感知 | 能否验证经验 |
|------|---------|-------------|
| AI 顺利解决 | 无感知 | **不能** — 不知道是哪条经验起作用 |
| AI 卡住，用户指导后解决 | 有感知 | **能** — 失败本身就是验证数据 |

**结论**：成功是常态，不需要验证；失败才是数据来源。

## 2. 经验生命周期

```
用户纠正 AI
     ↓
提取/修正经验 ──→ draft (草稿)
     ↓ 应用
遇到障碍？ ──否──→ 继续（无记录）
     ↓是
用户介入指导
     ↓
fail_count + 1
     ↓
修正经验内容
     ↓
fail_count = 0 ──→ verified（从未失败）
fail_count ≥ 2 ──→ failed（需修正）
```

### 状态定义

| 状态 | 含义 |
|------|------|
| draft | 新提取或正在修正中 |
| verified | 应用过且从未失败 |
| failed | 频繁失败，需要修正或归档 |

### 升级/降级规则

| 条件 | 状态变化 |
|------|---------|
| 首次提取 | → draft |
| 应用后 fail_count ≥ 2 | → failed |
| failed 经验被修正 | → draft（重新验证） |
| verified 后首次失败 | → draft（触发修正） |

> **不再有"成功计数升级"** — 成功不需要计数来证明。

## 3. 触发 /mine 的信号

### 3.1 触发时机

当用户纠正 AI 时，触发 /mine：

```
用户纠正 AI
     ↓
AI 意识到自己使用了不合适的经验
     ↓
主动说："这次我用了 xxx 经验但不太匹配，是否需要 /mine 提取一下？"
     ↓
/mine 激活
```

### 3.2 触发信号

| 信号 | 说明 |
|------|------|
| 用户说"不是这样做" | 纠正了 AI 的做法 |
| 用户说"应该先..." | 给出了正确的方向 |
| 用户说"你漏了..." | 补充了遗漏的步骤 |
| 用户说"我来告诉你" | 直接传授方法 |
| AI 意识到经验边界不清 | 主动承认不确定 |

### 3.3 不触发 /mine 的情况

- 简单问答
- AI 顺利解决，用户无感知
- 用户说"可以提取一下" — 这种情况用户不是感知到失败，而是感知到成功想分享，但这是稀有情况

## 4. 失败分析协议

当用户纠正 AI 后，经验矿工执行：

### 4.1 失败点定位

```
识别：
  - AI 在哪个环节卡住？（搜索？理解？实施？验证？）
  - 卡住时的表现？（重复尝试？方向错误？遗漏关键信息？）
  - 用户如何纠正？（提示方向？给出具体方案？纠正理解？）
```

### 4.2 经验问题分类

| 问题类型 | 判断标准 | 处理方式 |
|----------|---------|---------|
| **经验缺失** | 没有可用经验覆盖此类任务 | 新建经验 |
| **经验有误** | 现有经验内容本身错误或过时 | 修正经验内容 |
| **边界不清** | 经验适用范围定义模糊 | 补充适用边界 |
| **应用错误** | 经验本身正确但 AI 使用不当 | 强化应用指南 |

### 4.3 修正记录

每次用户纠正后，更新相关经验的元数据：

```yaml
---
name: <经验名称>
metadata:
  fail_count: <失败次数>
  last_fail: "<最近失败日期>"
  corrections:
    - date: "2026-04-07"
      fail_point: "AI 在第三步遗漏了边界检查"
      user_guidance: "需要先确认输入数据格式"
---
```

## 5. 经验提取流程

### 第一步：识别失败

用户纠正 AI → 识别这是一个失败点。

### 第二步：分析纠正

理解用户纠正的内容：
- 用户为什么这样纠正？（揭示了 AI 的什么盲点）
- 这个纠正是否可以泛化为一条经验？

### 第三步：定位相关经验

- 有相关经验 → 修正 + 记录 fail_count
- 无相关经验 → 新建经验

### 第四步：提取新经验（如有）

按模板创建（状态：draft）

### 第五步：更新索引

在 `experience-index` 中更新条目。

---

## 6. 经验清理机制

| 状态 | 清理条件 | 处理方式 |
|------|---------|---------|
| draft | 超过 30 天未被应用 | 降为 inactive |
| failed | 连续失败 3 次 | 修正或归档 |
| verified | 长期稳定 | 保留 |

---

## 7. SKILL.md 元数据格式

```yaml
---
name: <经验名称>
description: <一句话描述>
metadata:
  category: <分类>
  status: draft | verified | failed
  created: "<创建日期>"
  fail_count: 0      # 失败次数
  last_fail: null    # 最近失败日期
  corrections: []     # 修正记录
---
```
