# 分析交接后的落档补位流程

## 第一步：判断是否属于“分析已完成、执行未完成”

出现以下信号时，按交接补位处理：

1. 子智能体已经给出明确结论、问题清单或文档草稿
2. 失败原因不是分析错误，而是执行上限、工具调用中断、上下文结束等
3. 仓库中尚未真正写入目标文件，或只完成了部分同步

## 第二步：把子智能体输出视为“候选事实”，先核对再落档

1. 提取子智能体的核心结论：验收结论、问题分级、文件名、落档位置
2. 回到仓库核对目标目录和现有文档规范
3. 只补写已被证实的内容，不把未经复核的推断直接写入正式文档

## 第三步：由主智能体完成正式落档

1. 创建或补全正式文档（如 review、problem、STATUS、tasklist）
2. 保持命名、编号、链接格式与仓库既有约定一致
3. 在主文档中引用拆分后的问题单，避免信息只停留在聊天记录中

## 第四步：补做交叉同步

1. 确认 review 文档已写明验收范围、依据、结论与整改优先级
2. 确认 problems 文档已单独编号并可从 review/STATUS/tasklist 回链
3. 确认周状态文档和任务清单已同步反映“已验收 / 未通过 / 待修复”状态

## 第五步：向用户报告“分析完成”和“落档完成”是两个里程碑

1. 明确说明子智能体完成了什么分析
2. 明确说明主智能体实际写入了哪些文件
3. 如果仍有未落档部分，要单独列出，不要让用户误以为仓库已全部同步

## 关键原则

- 子智能体的分析结果可以复用，但正式文档必须由当前执行者确认后再写入
- 先补齐仓库事实，再汇报结果；不要把“建议写入”当成“已经写入”
- 交接场景优先保证可追溯性：结论、问题单、状态同步三者缺一不可
- 如果失败原因是分析质量问题，而不是执行中断，则不适用本流程

## 边界与不适用场景

- 不适用于子智能体结论互相冲突、无法确认真实性的情况
- 不适用于需要重新做完整调研的任务；此时应重启分析而不是直接落档
- 不适用于仅口头总结、无需写仓库文档的轻量任务
