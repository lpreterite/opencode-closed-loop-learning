# 反模式：混合范围提交

## 识别信号

- 用户明确说“只提交某个目录/某类文件”
- 工作区同时存在其他目录的未提交改动
- 准备提交时使用了过宽的暂存范围，如 `git add .`
- 提交说明聚焦某一主题，但实际包含 design、task、docs 等多类无关变更

## 规避策略

1. **先确认提交边界**
   - 从用户原话中抽取允许提交的目录、文件类型或专题
   - 不确定时先问，不要默认把当前工作区全部提交

2. **只审查范围内变更**
   - `git status` 看全局改动
   - `git diff -- <path>` 只检查目标范围
   - 如有必要，明确告诉用户还有哪些改动被排除在本次提交外

3. **只暂存范围内文件**
   - 使用精确路径暂存，如 `git add docs/product`
   - 避免使用会吸入无关文件的宽泛命令

4. **提交后复核**
   - 用 `git show --stat --name-only HEAD` 或 `git status` 检查本次提交内容
   - 确认未把 design/task 等无关目录带入

## 正确做法

当用户说“提交 product 这个文档变动”时：

1. 先查看全部改动，识别还有哪些非 `docs/product/` 变更存在
2. 明确本次只提交 `docs/product/` 相关文件
3. 仅暂存 `docs/product/` 路径下的变更
4. 提交后向用户说明：其他目录改动仍保留在工作区，未并入本次提交

## 边界说明

- 若用户说“把当前所有改动都提交”，则不属于此反模式
- 若范围内文件依赖范围外文件共同提交，应先向用户说明并请求确认扩大发送范围
